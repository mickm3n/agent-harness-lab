# 實戰班任務卡

各自操作，自己的 repo 自己改。每一關的驗收都機械可觀察，過沒過自己看得到。

流程固定：**先寫驗收條件 → 要計畫（不動檔）→ 核准後小步實作（子代理先寫測試）→ 先自審：測試三類齊不齊、子代理審 diff → 審第二層 → 資安檢核**。

---

## Issue #1（主線，必做）

**標題**：庫存不足時，出貨分配總量少於庫存

**背景**：倉儲回報 `widget` 庫存明明有 10 件，跑完出貨分配後只分出 9 件，剩 1 件留在倉庫沒人拿到。
可以直接重現：

```python
from app.allocation import allocate
allocate(10, {"A": 1, "B": 1, "C": 1, "D": 30})   # 加總只有 9
```

**影響範圍（預期）**：`app/allocation.py`，可能連帶 `app/fulfillment.py` 的呼叫端。

**不可變動**：`docs/api.md` 的契約；訂單 dict 的欄位；**不得為了讓測試通過而修改既有測試**。

**驗收條件**：由你們自己寫（見下方範本），至少三條，其中一條是邊界情境。

---

## Issue #2（加做，做完 Issue #1 的人再做）

**標題**：任何人都能執行出貨分配

**背景**：`run_fulfillment()` 沒有檢查呼叫者角色，一般客戶也能跑。契約規定只有 `staff` 與 `admin` 能執行（見 `docs/api.md`）。

**不可變動**：同 Issue #1；權限判斷要沿用專案既有的慣例，不要另寫一套。

---

## 驗收條件範本

寫**行為**，不寫實作。每一條都要能被一個測試證明。

```
AC1（正常路徑）：當 ______ 時，______ 應該 ______
AC2（失敗路徑）：當 ______ 時，應該拋出／回傳 ______
AC3（邊界情境）：當 ______ 時，______ 應該 ______
```

反例：「修好 allocate」「程式碼要乾淨」——這兩句無法被測試證明。

## 提示詞

**第一輪：只要計畫**（用 Plan mode，或在提示詞明講不得修改任何檔案）

```
請先不要修改任何檔案。

任務：<貼上 Issue 標題與背景>
驗收條件：<貼上你們寫的三條>

請先：
1. 讀 CLAUDE.md 與 docs/api.md。
2. 找出這個行為的實作、呼叫端、既有測試。
3. 提出修改計畫：會動到哪些檔案、每個檔案改什麼。
4. 指出一個你認為最大的風險，以及你會怎麼驗證它。
5. 等我核准後才可以動手。
```

**第二輪：核准後修改**

```
採用你的計畫。只修改你剛剛列出的檔案。
1. 用一個子代理，只根據驗收條件與 docs/api.md 寫測試，
   不要讓它讀 app/ 的實作；寫完確認測試目前是紅的。
2. 再修改實作，讓它們變綠。
3. 跑 lint 與完整測試，把原始輸出逐字貼給我；如果你沒有實際執行過，請明講。
4. 不得為了讓測試通過而修改既有測試。若你認為某個既有測試本身有錯，停下來說明理由，等我決定。
5. 回報：diff 摘要、測試結果、未解風險、需要人工確認的項目。
```

**第三輪：自我審查**

```
請用一個子代理審查目前的 diff（git diff），只回報結論：
- 有沒有超出計畫範圍的修改
- 有沒有驗收條件沒有對應的測試
- 有沒有你自己也不確定的地方
沒有問題就明講「沒有發現問題」。
```

## 卡住了

- 環境或登入問題：先跟旁邊的人一起研究；大問題直接打斷講師，全場一起解決。
- agent 停下來問你要不要改既有測試：**這就是要你決定的時刻**，不要直接說好。先看 `docs/api.md`，自己算一遍。
- 改壞了：用 Claude Code 的 rewind／checkpoint 回到上一個乾淨狀態，或 `git checkout -- .`。
